## Family sameness

Not the same in the way the pages need.

One build, yes. Only the fee, no. The fee does not differ.

The builder is one program. Every family is a genesis and then hops of one shape. The minter output is one constant. The token output is one constant, the size the plan already calls about 1 tKAS locked per landed hop. The storage cap is one constant. The hop line carries the funding coin and a nonce. It does not carry a fee rate.

The rate is one value for that process. It is fixed when the process starts. The floor is 100. The sender starts one builder process and passes one rate. The sixteen-family configs I opened set that one rate. The family rows name a family, a key, and a launch path. They do not name a fee. As opened, families 1–13 and families 14–16 pay the same rate.

A second builder process is the wrong fix. The sixteen run together, and this build opens one builder. Two processes would also be a way to put the cohorts on different nodes, which round 4 already refused.

The fee sompi is the mass times the rate. A higher rate takes a larger fee from the funding coin, so the change output is smaller. Storage mass is computed from the values, so it can move with the rate. I did not build a hop at 100 and at 200, so I did not measure that move. The token output stays the one constant either way. The program stays the one program. A mass gap, once the two rates exist, is the fee's own effect. It is not a second design.

Coin size is not a cohort field in the builder. The splitter takes one target size for a batch, and the sender then keeps families off each other's coins. I did not open the live pool, so I do not confirm the sixteen coins are one size. If they are mixed, the method file says so and does not call the fee the whole cause.
